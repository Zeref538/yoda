Offline data cleaning agent

YODA

qwen3.5 4B · runs on your own laptop

Everyone wants AI on their spreadsheets and nobody wants the spreadsheet leaving the building. So the AI here never reads a single row. It gets a summary with the names and numbers blanked out, writes a cleaning plan, and you approve it. Then ordinary code does the actual changes, and logs every one.

A local Ollama model plans from a redacted profile (schema, statistics, masked samples) under a JSON schema. Deterministic pandas executes the approved plan with an audit log. Scored against a corruption manifest of labelled errors, including a false-fix rate, and against a rule-based baseline.

02The privacy line

"How do you know the AI didn't mess up the data?" It can't. It never touches it.

Raw values flow profiler to executor only; the prompt path is redacted and tested

The AI's only job is to say what should happen: "these dates come in three styles, make them one". Doing it is left to plain code that works the same way every time. So the AI can suggest something silly, and you'll see it in the plan before anything changes. It still can't quietly rewrite a number.

The planner receives the profiler's JSON: dtypes, null share, unique counts, detected formats, outlier flags and regex-masked samples. The executor is the only component with the dataframe, keeps the original, and writes an audit log of rows affected per step.

A test holds the line

tests/test_redactor.py seeds real-looking names, emails and phone numbers into a table, builds the exact prompt the model would get, and fails if any of them appear in it.

Everything runs on one laptop through Ollama. No account, no API key, no internet once the model is downloaded.

The local web UI binds to 127.0.0.1 and, since this audit, also refuses any request whose Host header is not localhost, which closes DNS rebinding.

03The benchmark

Break clean tables on purpose, write down every break, then check the repair

Six seeded datasets, a labelled corruption manifest, and a scorer with a false-fix rate

Because every planted mistake is on a list, the scorer can say three things: did the plan spot it, did the output fix it, and did anything that wasn't broken get changed anyway. That last one is the number most tools don't show you.

Detection counts an error as found when the plan targets its column with the right tool. Fix compares the output cell with the clean original. False-fix is changed cells that were never corrupted, over all clean cells checked.

    05What broke

    The best score this project ever posted was not the AI's

    Three findings, one of which withdrew the published headline

    The v3 headline was the safety net's score

    The backup plan did exactly what it was built to do. The trouble is it did it silently, and the backup is the rule-based planner, so the score went up when the AI failed. The benchmark counted the output and never checked who made it. Now every results table names each dataset that fell back.

    Each fallen-back v3 plan failed with JSONDecodeError: Unterminated string three times, the reply cut off mid-JSON. v3 tripled the system prompt, to about 3,000 tokens with the profile, against Ollama's 2k-4k default context on a laptop. Setting num_ctx to 8192 fixed it: zero fallbacks on rerun. results.md now prints a "Not agent output" line per fallback.

    07Run it yourself

    Install it, point it at a messy file, approve the plan

    Install, clean, reproduce the benchmark

    git clone https://github.com/Zeref538/yoda && cd yoda && pip install -e ".[web]" 
    ollama pull qwen3.5:4b
yoda clean data.csv                 # plan, approve, clean
yoda clean data.csv --dry-run       # plan and report, change nothing
yoda web                            # spreadsheet UI on 127.0.0.1
python -m benchmark.run_benchmark --planner llm --model qwen3.5:4b

    Works on CSV, Excel and SQLite. The model is about 3.4 GB and runs on a laptop CPU.
